# LingoMend：TextEdit 优先的用户场景与需求草案

日期：2026-10-09。状态：产品方向已确认，按 TextEdit T1–T4 分阶段实现。

## 1. 结论与产品定义

LingoMend 应帮助用户完成**自己的英文表达**：会写的先写，不会写的用中文占位；需要帮助时，结合语境把表达补完整、修正确，愿意学习时再解释。它不是默认全文翻译器、代写器，也不是每次都要打开大窗口的润色工具。

产品原则：**The goal is to need us less.**

建议的首个完整体验：后台安静运行 → 用户在 TextEdit 写作 → 按快捷键 → 根据选区或光标定位表达 → 出现不抢焦点的轻量候选 → 用户接受或忽略 → 继续写作；解释、收藏是可选分支。

对“英文短句里有中文占位”的处理：**按当前句子理解，以自然、准确的英文表达为目标。** 保留可用英文，修正必要的搭配和句法。`I very like 这个方案.` 应一起修正为 `I really like this approach.`；不能因“只改中文”的技术限制留下不自然的英文。修改对照帮助用户发现并学习原有英文的问题。

用户此次明确提出快捷键触发，因此建议将“按需触发”作为近期默认体验。之前的停顿自动候选作为后续可选实验，而不是当前必需能力。本草案不修改现有运行设置。

## 2. 调研方法与证据边界

本轮是桌面调研：原始产品讨论、用户在开发过程中的反馈、当前源码审查、相关产品官方说明、研究论文摘要。没有进行新用户访谈、竞品实机横评或学习效果实验。

- 用户需求证据：中英混合写作、减少打断、保留现有输入法、按需学习、先完成 TextEdit 闭环。
- 实现证据：当前 main 的源码，审查基线 `261cc62`；这些事实不是完整产品验收。
- 外部证据：只用于理解交互选择与风险，不证明 LingoMend 的市场规模或学习增益。
- 下文优先级、范围上限和体验指标均为产品建议，需要通过用户试用校正；不声称场景列表涵盖所有用户。

原始讨论中的旧建议只是参考材料。已有快捷键、读取器和 Provider 是实现基础，不应反过来限定产品只能处理最近一个中文词。

### 2.1 相关产品提供了哪些启发

| 来源 | 官方页面可确认的能力 | 对 LingoMend 的启发，不是照搬要求 |
| --- | --- | --- |
| DeepL Write | 区分单词替代、整句改写、全文风格/语气调整，并提供不改动的术语列表 | “补词”“改句”“改风格”需要不同的修改权限；专业术语应可保护 |
| Grammarly | 在写作中的选定文本上提供翻译，用户接受或复制结果 | 原地完成任务有价值，但选区、翻译和接受仍应有清晰边界 |
| Apple Writing Tools | 将校对、改写、语气调整、概括列为不同任务 | 一个快捷入口可以智能推荐任务，不等于无区别地重写 |
| Effidit 技术报告 | 将上下文短语润色、句子改写、句子扩展等分开描述 | 上下文补表达是独立任务，不需要以自动续写为前提 |

上述功能依据分别来自 [DeepL 官方帮助](https://support.deepl.com/hc/en-us/articles/9710730337820-Customize-your-text-with-DeepL-Write)、[Grammarly 官方帮助](https://support.grammarly.com/hc/en-us/articles/27518589299725-Introducing-Grammarly-s-translation-feature)、[Apple 官方用户指南](https://support.apple.com/guide/mac-help/writing-tools-write-improve-summarize-mchldcd6c260/mac)、[Effidit 作者技术报告](https://arxiv.org/abs/2208.01815)。这里只比较公开描述的任务结构，不推断其他产品没有学习功能，也不承诺其当前版本在本机可用。

### 2.2 研究对产品方向的约束

关于作者真实性的研究访问了专业作者，并指出作者对个性化帮助的期待涉及自身成长。本项目据此保留作者表达和学习机会：修正必要的语言问题，保留观点、语气和可用措辞。[作者论文](https://arxiv.org/abs/2411.13032)

一项 AI 协同写作研究发现，在其研究情境中，阅读和评判 AI 建议会占据写作过程，并影响构思方向。LingoMend 据此采用按需求助：用户先表达，再请求语言帮助；候选保持克制，未完成的观点留给作者继续构思。[Reactive Writers](https://arxiv.org/abs/2603.10374)

二语写作个案研究展示了一位博士生结合 ChatGPT 写作并保持作者主体性的过程。LingoMend 将写作帮助和主动学习连在一起：先完成自己的表达，再按需理解搭配、句法和可复用表达。长期学习效果通过后续独立使用与试用研究评估。[二语写作个案研究](https://arxiv.org/abs/2310.10903)

## 3. 调整前基线的问题（`261cc62`）

| 当前实现事实 | 用户体验后果 | 应调整的需求 |
| --- | --- | --- |
| 无选区时使用短输入框或换行分隔段落，不是真正的句子边界 | 一个段落的几句话可能混在一起 | 以光标所在句子为默认工作单元 |
| 显式选区同时充当上下文 | 只选中文后，英文搭配语境可能丢失 | 将只读上下文与可修改选区分开 |
| 候选只替换一个中文片段，左右英文必须完全不变 | 原有语法错误不能修正；多个缺口不能完整处理 | 支持最小补缺和必要整句修正 |
| 片段请求：中文最多 40 个 UTF-16 单位，左右各最多 200 | 长句上下文会被截断，长度限制不等于语义边界 | 按完整句子建立请求边界；超限显式提示 |
| 无选区缺口检测受光标与最近中文片段距离限制 | 光标放在句中、缺口离光标稍远时可能没有结果 | 定位句子后，处理该句中的表达问题 |
| 纯英文、未选中的纯中文不属于当前缺口主流程 | 用户按快捷键时可能不知道为什么没反应 | 明确处理英文纠错、整句翻译、无需修改等结果 |
| 网络输出经过结构和编辑边界校验 | 可以约束返回格式，但不保证翻译含义正确 | 单独建立语义、事实和语气保真验收 |

审查入口：`Sources/PlatformBridge/ParagraphScopeResolver.swift`、`Sources/PlatformBridge/InlinePlaceholderResolver.swift`、`Sources/MVPFlow/InlineProposal.swift`、`Sources/CoachCore/ExpressionProvider.swift`。

调整前的片段流程会提供有限左右上下文，但只允许补中文片段。新的 T1 交付范围见 [TextEdit T1 体验步骤](../textedit-t1-experience.md)：当前句理解、句子级建议、选区边界和修改对照。安全接受、撤销与完整学习链路随后接入。

## 4. 谁在什么时候使用它

近期按任务而非 CEFR 等级定义用户。能写一部分英语，但会在词汇、搭配或句法上卡住，就属于目标场景。不要用中文占比自动给用户定级。

### 4.1 研究与技术写作

用户正在写论文笔记、实验说明、技术讨论。最重要的是术语、数字、条件和判断强弱准确，其次才是自然表达。`may` 不能变成 `will`，`0.5 A` 不能被改成另一个参数；ZVS、DAB 等缩写不能被无故展开或改名。

### 4.2 工作与日常沟通

用户正在组织邮件、项目说明或日常消息。希望迅速补出自然表达，不愿跳转到聊天工具。是否礼貌、正式或简洁应由用户目标决定，不凭应用名称猜测。

### 4.3 以写促学

用户先完成任务，再对刚才不会的表达查看一句解释、搭配和可替换说法。收藏意味着“值得复习”，接受意味着“这次用了”，都不能直接当作“已经掌握”。

TextEdit 可以承载上述任务的合成试用；当前阶段不要求接入邮件、聊天客户端或浏览器才证明场景成立。

## 5. 用户场景目录

P0：TextEdit 核心闭环必须覆盖。P1：核心闭环稳定后补充。P2：后续独立设计，不阻塞 MVP。

### 5.1 表达生成与修正

以下输出是验收示例，不要求模型逐字一致；含义、编辑范围和自然程度才是标准。

| ID | 用户场景与输入 | 用户真正需要的帮助 | 预期行为 | 优先级 |
| --- | --- | --- | --- | --- |
| E01 | `This works 轻载条件下.` | 不会一个专业短语 | 结合句子补为 `under light-load conditions`，其他字不变 | P0 |
| E02 | `I am 负责 this project.` | 不会搭配而非单词 | 补为 `responsible for`，不是孤立的 `responsible` | P0 |
| E03 | `The main advantage is 可以减少损耗.` | 中文部分承担句法结构 | 可以补为 `that it can reduce losses`，不强求一个词对应一个词 | P0 |
| E04 | `I very like 这个方案.` | 缺口和英文结构都不自然 | 提议 `I really like this approach.`，标记还修正了英文 | P0 |
| E05 | `I discussed about 这个方案 with him.` | 中文替换后仍有英语错误 | 删除多余 `about`，不能只给中文翻译后声称句子已正确 | P0 |
| E06 | `We need 降低损耗 without 增加成本.` | 同一句有多个缺口 | 统一考虑本句两处表达，不只补光标最近的一处 | P0 |
| E07 | `She go to the lab yesterday.` | 没有中文，但怀疑语法 | 最小纠错 `She went to the lab yesterday.` | P0 |

| E09 | `这个方法可能会降低损耗。` | 暂时整句不会说 | 默认英文目标下提供整句翻译，保留“可能”，标记任务为翻译 | P0 |
| E10 | `The result is 很好.` | 简单词已有多个可行译法 | 优先朴素保真表达，不擅自升级为“突破性结果” | P0 |

| E12 | `We need 处理 this signal.` | 中文有多义，语境不足 | 不能确定是 process/filter 时给简短澄清或保守候选，不编造操作 | P0 |
| E13 | 只选中长句中的一个中文短语 | 用户只授权补这个位置 | 读取所在句作为只读语境，默认只改选区；需整句调整时另行授权 | P0 |

| E15 | 显式选中多个句子或整段 | 用户有意批量处理 | 展示更清晰的差异审阅；未实现时直说暂不支持，不能暗中只做一小部分 | P1 |

## 6. Smart Scope：四种范围必须分开

| 范围 | 含义 | 建议规则 |
| --- | --- | --- |
| 系统读取范围 | 从 TextEdit 控件拿到的本地文字 | 当前桥接可能读取整个聚焦文本控件，再本地定位；不能宣传“系统只读取一句” |
| 语义上下文 | 为理解表达而使用的内容 | 默认当前句子；不自动附带全段、全篇、历史或剪贴板 |
| 网络发送范围 | 真正传给模型的内容 | 仅目标句与必要的选区信息、任务偏好；不发送整控件、路径和应用身份 |
| 可修改范围 | 用户授权接受建议后能改变的文字 | 有选区则选区；无选区则当前句内的最小必要修改；句外不可改 |

当前桥接读取的是聚焦控件的 `AXValue`，取得内容后检查长度上限；因此本地读取与外发不是一回事。后续技术实现可以研究更小范围读取，但现阶段隐私说明必须符合实际能力。

### 6.1 无选区时

1. 快捷键触发后，取得聚焦编辑器与光标快照。
2. 找到光标所在句子，包括光标左右内容；不是只看前面的中文。
3. 在句末句号后、尚未输入下一句时，使用刚结束的句子。
4. 两句之间仅有空格时默认前一句；已经进入后一句文字则使用后一句。
5. 新的空白段落不自动回头修改上一段；用户可把光标放回原句。
6. 无句号的标题或短列表项可以作为一个表达单元；软换行只是视觉折行，不能当作新句子。
7. 默认只提出该句的修改，不扩展至整段。

句子定位必须覆盖 `Dr.`、`e.g.`、`Fig. 2`、`0.5`、网址、引号、括号、中英文句号与问号等，不能只按每一个 `.` 切割。无法可靠定位时，显示实际目标片段并请用户选定，不默默读整个输入框。

### 6.2 有选区时

- 一个词或短语：选区是编辑边界；其所在完整句子可以作为只读上下文。候选明确说明“只改选中内容”。
- 一个句子：该句是处理目标。
- 多句/整段：属于显式较大范围请求，放在 P1。P0 应提示暂不支持，而非无声扩大或缩小。
- 如果只修改选区不能形成正确句子，提供“需要整句修正”的入口；用户选择后才扩大权限。

这样既不要求用户每次先选中文，也不取消选区作为精确控制手段。

### 6.3 长度与隐私建议

首版可以暂定当前句上限 600 个 UTF-16 单位，作为成本与界面容量预算，不是语言学标准，也不是最终定值。超限明确提示选择较短表达，不悄悄截断主语、否定或条件。

默认不附加相邻句。确实依赖前文时，由用户主动授权加入有限相邻语境。远程模型会看到发送的写作内容，应在设置中明确说明；Keychain 保存密钥不意味着文字在本地推理。

仅请求时读取，不做后台全文扫描、键盘内容记录或剪贴板监控。接受前安全检查期间的再次读取属于当前操作，不用于长期记录写作。

## 7. 意图识别：一个入口，有限任务，不读心

默认快捷键含义建议为：“帮助我把当前表达说正确、说自然”。目标语言默认英文，由设置决定。

| 本地可观察信号 | 推荐任务 | 模型与界面的责任 |
| --- | --- | --- |
| 中英混合 prose | 补表达，必要时最小整句修正 | 判断汉字是否真是缺口；保留可用英文，不强行拆成逐词翻译 |
| 英文 prose | 最小纠错与明显搭配修正 | 正确时返回无需修改；不默认做文风升级 |
| 中文 prose | 英文表达/翻译 | 保留事实与语气，标记“整句翻译”；不当作能力低的证据 |
| 专名、引文、代码、模糊短语 | 保留、澄清或暂不处理 | 不以汉字比例硬判意图，也不编造上下文 |
| 用户明确选择礼貌/学术/简短等目标 | 显式风格任务 | 和默认纠错区分，后续提供 |

建议本地先定位范围、检查空白与非编辑区域，再由一次模型请求产生候选与任务标签。无需每次先付费调用一个“意图分类器”，再调用第二次生成；学习解释只有用户请求时另行生成。

模型输出可区分：有建议、已经合适、需要澄清、暂不支持。不要把所有情况都显示为没有反应。

“最小必要修正”不是简单限制改几个字符。例如 `I very like ...` 可能必须改英文结构，但仍不能凭空增加理由、转折或夸赞。模型自报置信度、声称“原意不变”，都不是独立语义证明。

接受范围和文本位置由本地确定；模型不能指定系统控件、焦点、剪贴板或任意写入位置。返回的改写必须在本地计算差异、检查边界；安全策略不只靠提示词。

## 8. 轻量交互的完整流程

常态：菜单栏后台运行，不显示主窗口，不主动分析正在写的内容。

请求：快捷键触发后，光标附近出现紧凑候选。补词时显示短语；整句修正时显示句子与简短变化标记。通过可选“查看变化”知道到底动了哪里；较大变化不能以只有一个短词的界面伪装。

接受：一个明确按键接受，Esc 取消。接受键要在 TextEdit 验证与原生输入法、换行、Tab 缩进的冲突后确定；本草案不直接把全局 Enter 或 Tab 设为接受键。候选不存在时，普通输入按键完全不受影响。

写回：候选可接受不等于立即替换；替换前再次检查源文本、范围、焦点和文档是否仍一致。接受后保持编辑器焦点，并让光标合理落在修改后的表达位置；选区外内容不变。

学习：用户主动展开“为什么”，才出现解释卡片。普通接受不必读解释、点确认或收藏。菜单保留最近一次帮助入口，使接受后也能学习。

过期：继续输入、切换文档或焦点发生变化，旧候选不再可接受。不能重新在文档里搜索相同中文并替换另一处。

错误：只给短而可行动的反馈；编辑器不被锁住，不展示重复大弹窗，不自动连续重试收费请求。

## 9. 学习与成长应怎样衡量

近期只建立“使用后可理解”的闭环：原表达 → 自然表达 → 本句为什么这样用。解释优先讲一个关键点，不展示长篇语法课。

后续可以本地保存用户主动收藏的表达卡片，再设计主动回忆或再使用。需要区分：获得建议、接受建议、收藏、主动回忆、在新语境独立使用。它们证据强度不同。

只在按快捷键时取得文本，系统并不知道用户所有写作，也不能可靠区分手打与粘贴。因此不承诺自动发现所有独立复用；未来需单独设计用户主动提交或明确同意的观察机制。

不以英文字符占比、API 调用数量或连续签到直接代表英语能力。CEFR 等级、掌握分数、周报和 gamification 都不进入当前核心闭环验收。

## 10. 用场景指导模块调整，而不是推倒重写

| 能复用的基础 | 围绕需求要补上的能力 | 对应场景 |
| --- | --- | --- |
| 菜单栏、快捷键、模型配置、Keychain | 安静的显式触发主流程与明确状态 | I01–I04、I06 |
| 文本快照、范围类型、替换前检查 | 当前句解析；只读上下文与编辑边界分离 | E13–E14、B08、I03 |
| Provider、网络取消、结构化返回校验 | 句子级最小修正、多个缺口、无需修改与澄清 | E01–E12 |
| 轻量候选与 diff 基础 | 补缺/整句修正/翻译标签，按需查看变化 | I02、I04 |
| 替换桥接 | TextEdit 稳定写回、原生撤销、格式和光标保持 | I05 |
| 解释服务、本地学习模型 | 接受后回看解释，之后再做主动收藏 | I07–I10 |

这些是责任划分建议，不是本轮 API 或架构实现。Swift 原生轻量路线可以保留；真正需要改的是产品契约，不是先换语言、换模型或引入大型 Agent 框架。

## 11. TextEdit 优先的分阶段计划

当前研究草案优先于旧计划中“只补一个中文片段”或“先扩展多应用”的方向；经用户确认后，再同步修改正式阶段计划与设计决策，避免两个版本同时指导实现。

### T0：确认场景与默认行为——本轮

产出：本草案、范围策略、场景目录、验收清单。明确默认按需触发、当前句语境、最小必要修正、用户接受、按需解释。没有修改应用代码或运行配置，没有执行付费请求。

决策门：用户认可默认处理方式与近期范围，才能开始 T1。

### T1：把“当前表达”识别正确

实现：TextEdit 的句子范围解析；选区与上下文分离；补缺、英文最小纠错、整句中文表达、无需修改和澄清等有限任务；句内多缺口；本地保护与响应校验。

先用固定响应和自动化用例证明范围，再用小量合成文本检查真实模型，不把模型接入等同需求通过。此阶段主要验收“读对、建议对”，不宣称写回闭环已完成。

交付：一版可体验候选的 app、对应自动化测试、范围/语义人工测试表；完成阶段本地提交和远程推送，只推源码和非敏感文档。

### T2：完成轻量接受与安全编辑

实现：不抢焦点候选、明确接受/取消、候选过期、源快照检查、TextEdit 写回、一次原生撤销、富文本与光标位置保持、失败时不写入。

决策门：TextEdit 纯文本和基础富文本都通过基本接受/撤销。系统辅助功能写入并不天然保证目标应用撤销正确，应在 TextEdit 做小范围技术验证；失败时报告具体限制并调整方案，不回退成未经批准的整框覆盖或剪贴板接管。

T2 实现补充（2026-10-09）：用户已明确允许仅在接受时临时借用剪贴板完成一次 TextEdit 原生编辑。
采用局部富文本原生粘贴，保存/有条件恢复原剪贴板；不可可靠保存的数据或不支持的格式拒绝操作。
详细边界见 [ADR 0005](../adr/0005-textedit-native-acceptance.md) 与 [T2 体验步骤](../textedit-t2-experience.md)。
原生编辑器自动测试通过后，仍需真实 TextEdit 用户验收才能通过上述决策门。

交付：一版完整“写—求助—接受—继续写”的 app，用户按清单试用反馈。阶段提交/推送后停止，先调整再进入 T3。

### T3：补齐按需学习与日常可用性

实现：短解释、接受后回看、必要的本地收藏入口、请求状态和成本保护。收藏库属于 P1，可在核心稳定后以小版本追加；不以实现长期掌握模型作为近期完成条件。

交付：在 TextEdit 完成写作与学习的基本闭环；用实际体验判断是否流畅，而不只看测试数量。阶段提交/推送后停止汇报。

### T4：体验收敛，再决定兼容性扩展

先连续几次 TextEdit 使用收集反馈：读错范围、改过头、补不自然、打断思路、接受/撤销失败、解释帮助不足。修复之后再考虑 Safari、VS Code 等适配。

暂不做：真正输入法、全局持续键盘监听、十应用兼容矩阵、自动全文扫描、模型路由平台、自动等级评分、学习周报或正式 TypeTide 底座迁移。

## 12. 用户可以帮助执行的 TextEdit 验收清单

使用新建合成文档，不使用真实研究、账号或工作隐私。以下是后续版本的验收要求，不表示当前版本已经支持。

每个案例记录：光标/选区、实际读取目标、候选是否保真、实际修改、一次撤销、是否打断。真实模型不要求和示例逐字一致。

| 编号 | 操作 | 验收要点 |
| --- | --- | --- |
| A01 | 正常输入 30 秒，不触发 | 无候选，无自动付费请求 |
| A02 | `This works 轻载条件下.`，无选区，光标句末，触发 | 结合本句补出工况表达；非缺口部分不变 |
| A03 | `I am 负责 this project.`，只选中文，触发 | 仍理解完整句子，补出带 `for` 的搭配；不改选区外 |
| A04 | `I very like 这个方案.`，无选区 | 候选修正英文结构，并清晰标记较大修正 |
| A05 | 一行两句，第二句有中文，光标第二句 | 第一整句不成为可编辑范围，接受/撤销不动第一句 |
| A06 | 光标置于句中，中文在光标右侧 | 使用完整当前句，不因中文在右边而漏掉 |
| A07 | 同一句两个缺口 | 两处共同处理，原意和英文约束保留 |
| A08 | `She go to the lab yesterday.` | 支持最小英文纠错 |
| A09 | `I made a decision yesterday.` | 明确无需修改，不强行润色 |
| A10 | 整句中文，包含“可能” | 可生成英文，保留不确定语气 |
| A11 | 含 `Dr. Li`、`0.5 A`、`e.g.` 的句子 | 句子不被缩写/小数错误切断，数值术语不变 |
| A12 | 未完成句、引文、中文专名 | 不代写观点，不把所有中文当缺口 |
| A13 | 请求后继续输入或切到另一文档 | 旧建议不能修改新文本或另一文档 |
| A14 | 接受一个候选，再按一次原生撤销 | 恢复这次修改；其他内容及基础富文本样式不变 |
| A15 | 接受之后再点“为什么” | 能回看本次解释；不强制联网获取解释才能接受 |
| A16 | 断网后触发，或连续触发多次 | 原文不变；提示简短；无收费重试循环或队列 |
| A17 | 超长句、多句选区、新空白段落 | 给明确范围/限制反馈，不自动扩大到整篇 |

接受安全、一次撤销、句外不变是硬门槛。建议质量则由用户判断是否准确、朴素、自然；程序校验不能代替这一步。

## 13. 试用反馈如何转化为需求

先由产品所有者在 TextEdit 做短期真实写作试用，反馈可匿名改写为合成例句；不要求上传真实原文。

每次不满意只需说清：我想表达什么、希望改哪里、候选哪里不对、是否打断思路。将其归类到范围、意图、表达质量、接受安全、学习价值或成本延迟，逐类改进。

待基本闭环稳定后，可以邀请少量有研究写作、工作沟通和日常写作需求的用户进行任务访谈。目的先验证场景与操作是否成立，不用小样本声称市场比例或学习效果。

近期指标建议：目标句定位是否正确、句外误改次数、候选是否改变事实/语气、接受与撤销是否成功、用户是否能直接继续写、解释是否回答了实际疑问。响应速度记录端到端体验和分布，不用单次接口耗时代表全部性能。

## 14. 已确认的产品决定

后续开发遵循以下原则：

1. 默认后台安静运行，由快捷键请求；自动停顿建议暂不作为默认。
2. 无选区时处理当前句子：优先补中文，必要时允许最小英文修正；有选区时只改选区，扩大范围需明确选择。
3. 默认不做高级润色、续写或改变语气；候选由用户接受，解释按需展开。

T1 的范围、模型契约和测试共同围绕这些原则展开。每阶段交付后，由用户体验反馈决定下一步调整。
